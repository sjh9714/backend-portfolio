# 이 사이트의 글쓰기 규칙

새 문장을 쓰기 전에 여기를 본다. 근거는 `~/Downloads/참고자료`의
『개발자를 위한 이력서 포트폴리오 완벽 가이드 2』(생각등대)와 주차별 커리큘럼,
그리고 웹의 다른 신입 백엔드 이력서·포트폴리오 예시다.

## 왜 이 문서가 생겼나

사이트를 훑어보니 제목이 이랬다.

> 행 잠금이 외부 호출 구간을 지키지 못하던 것을 상태 전이로 집는 방식으로 바꿔
> 두 인스턴스가 같은 작업을 가져가지 못하게 함 — **58자**

`상태 전이로 집는다`, `잔여석 공유 row`, `API 계약의 일급 상태`.
전부 **우리가 만든 말**이다. 읽는 사람이 해석을 해야 하고, 면접관에게는 그 시간이 없다.

가이드는 면접관이 하루 10~20개의 이력서를 본다고 말한다. 짧으면 1분, 길어도 5분 안에
판단이 끝난다. **읽는 순간 이해되지 않으면 없는 것과 같다.**

## 본보기로 삼는 문장

가이드가 좋은 예로 든 것:

```
데이터베이스 쿼리 최적화하여 응답 속도를 5초 → 500ms로 단축
질문 게시글 리스트 조회 시, 느린 응답 문제 발생 및 Redis 캐시 적용으로 평균 응답속도 350ms → 40ms 개선
```

가이드 자신이 쓰는 문체:

> "아키텍처라는 단어가 어렵게 느껴질 수 있지만, 사실 굉장히 직관적입니다."
> "쉽게 말해, 시스템 내부의 구성 요소들이 어떻게 연결되고 소통하는지를 나타내는 구조도입니다."
> "마치 가족 관계도를 그리듯…"

**어려운 것을 쉽게 풀어 쓴다.** 그게 이 바닥의 좋은 글이다.

## 규칙

### 1. 제목은 45자 안쪽 — 판단 기준은 "한 호흡에 읽히는가"

형태는 `[기능] + [문제] + [해결] + [수치]`.

```
✗  동일 좌석에 100명이 동시 예매할 때 중복 판매를 막기 위해 락 전략 3종을 같은 조건에서 비교하고 oversell 0건 확인  (58자)
✓  같은 좌석에 100명이 몰릴 때 나던 중복 판매를 비관적 락으로 막아 oversell 0건  (43자)
```

> **정정 (2026-08-08).** 처음엔 "35자 안쪽"이라 적었는데, 바로 위의 ✓ 예시가 43자였고
> 실제 제목 7개도 전부 38~46자였다. 규칙의 숫자가 처음부터 스스로와 어긋났던 것이다.
> 제목들은 한 호흡에 읽히므로 문제는 제목이 아니라 숫자였고, 숫자를 고쳤다.
> 길이는 수단이고 기준은 하나다 — **소리 내어 읽었을 때 숨을 다시 쉬지 않는가.**

### 2. 우리가 만든 말을 쓰지 않는다

남이 이미 쓰는 말이 있으면 그것을 쓴다. 표준 용어는 이런 것들이다 —
`응답 지연` · `실행 계획` · `조회 전용 DTO` · `인덱스 조정` · `재고 차감` · `데이터 정합성`.

| 우리가 만든 말 | 남이 쓰는 말 |
|---|---|
| 상태 전이로 집는다 | 상태 값으로 선점한다 |
| 잔여석 공유 row의 버전 충돌 | 잔여석 카운터 한 줄을 같이 고쳐서 |
| API 계약의 일급 상태 | 응답에 '확인 안 됨'을 그대로 담는다 |
| 저장 경계 | 저장이 끝난 시점 |

새 낱말을 만들고 싶어지면, 그건 대개 **아직 스스로 정리가 안 된 것**이다.

### 3. 결과는 before → after

숫자 하나만 적으면 좋아졌는지 알 수 없다.

```
✗  쓰기 p95 6ms
✓  쓰기 37ms → 6ms
✗  oversell 0건        (이건 예외다. 0이 목표인 값은 after만으로 뜻이 선다)
```

### 4. 한 문장에 쉼표는 두 개까지

세 개가 넘으면 문장을 나눈다. 나눌 수 없으면 아직 한 가지를 말하고 있지 않은 것이다.

### 5. 숫자는 근거 파일이 있어야 한다

`docs/facts/*.md`에 없는 숫자를 새로 쓰지 않는다. 재지 않았으면 재고 나서 쓴다.
잴 수 없으면 **왜 못 쟀는지**를 적는다(`pendingMeasurement`).

## 구조 (가이드 기준)

| | 기준 | 원문 |
|---|---|---|
| 프로젝트 | **3~4개** | "프로젝트는 3개, 많아도 4개 정도면 충분" |
| 이력서 — 문제 해결 | 프로젝트당 **3~4줄** | "최소 3줄에서 4줄 정도로 채워주는 것을 지향" |
| 이력서 — 단순히 구현 | 프로젝트당 **2~3줄** | "'구현'은 2줄에서 3줄 정도" |
| 포트폴리오 덩어리 | **4~5개** | "9개 중에서 담을 만한 핵심 요소 4~5개를 골라" |
| 덩어리의 제목 | 이력서의 그 한 줄 **그대로** | "추출한 이력서의 4~5줄이 그대로 '제목'이 됩니다" |
| 덩어리의 구성 | 제목 / 그림 / **문제 3 · 해결 3 · 결과 3** | "각각 3줄 정도로 정리해서, 총 9줄 내외" |
| 그림 | 구조·흐름·시퀀스. **앱 화면 캡처 금지** | "백엔드는 '기능 화면'이 아니라 '구조와 흐름'" |
| 결과 | 환경·부하·병목·개선 후 수치 | "적어주면 설득력이 확 올라갑니다" |
| 넣지 않는 것 | 코드 캡처 | "코드가 아니라 흐름과 근거로" |
| 구성 비율 | **기본기 60% + 강점 40%** | |

> 한때 이 표에 `해결 3~4줄`이라고 적혀 있었다. 원문에 없는 말이고, 그 탓에 덩어리가
> 9줄과 10줄로 갈렸다. **원문은 "각각 3줄"이다.** 세 칸을 3·3·3으로 맞춘다.

기본기는 커리큘럼 3~6주차가 그대로다 — **인덱스 · 트랜잭션과 락 · 서버 최적화 · Redis**.
가이드가 든 신입 기본기 예시도 같다(실행계획 분석, 캐시 적용, 동기·비동기 구분).

## 고르는 기준

가이드의 말 그대로다.

> **그 문제 해결 과정을 머릿속에 그림처럼 떠올릴 수 있는가.**

그릴 수 없으면 포트폴리오에 넣을 만한 난이도가 아니다. 다른 것을 고른다.
