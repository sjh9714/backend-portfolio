# 포트폴리오 글쓰기 기준

이 사이트는 읽는 사람이 **무슨 문제였고, 내가 어디까지 맡았으며, 어떤 근거로 결과를 말하는지** 빠르게 판단하도록 쓴다. 문장 길이나 불릿 개수를 맞추기 위해 필요한 조건을 빼지 않는다. 기술 용어는 실제 코드와 측정에 맞는 말로 쓰고, 낯선 말은 그 자리에서 풀어 설명한다.

## 홈과 이력서

홈은 FinMate·예매의 대표 사례 두 건을 읽는 순서대로 보여 준다. 각 항목은 프로젝트 맥락과 역할을 짧게 밝히고, 해당 상세 사례의 앵커로 바로 연결한다. 채팅·ETA·과금 프로젝트는 추가 목록에서 찾을 수 있다. 홈 문장을 고칠 때는 사례 본문과 주장 범위가 달라지지 않았는지 확인한다.

이력서는 FinMate, 좌석 예약, 채팅 세 프로젝트를 선별한다. 각 항목은 맡은 역할과 결과를 압축하고, 자세한 사례로 연결한다. PDF는 웹 이력서에서 생성한다. 내용·표현·인쇄 레이아웃·폰트가 바뀌면 `node scripts/resume-pdf.mjs`로 다시 생성한다.

## 프로젝트 상세

맨 위에서 서비스의 목적, 내 역할, 팀 구성, 담당 범위를 알려 준다. 그다음 문제 해결을 먼저 보여 주고, 서비스 화면과 실행 방법은 뒤에서 제공한다. 독자가 전후 맥락 없이 숫자부터 만나지 않도록 한다.

사례 하나에는 다음 내용을 둔다.

- **상황과 조건:** 어떤 사용자 흐름이나 실행 조건에서 문제가 나타났는가.
- **관찰한 원인:** 코드·쿼리·측정에서 무엇을 확인했는가. 가설과 확인된 사실을 구분한다.
- **대안과 선택:** 실제로 검토한 선택지와 채택 이유를 적는다. 비교 측정을 했다면 각 대안의 이름을 붙인다.
- **적용 과정:** 바꾼 경로와 검증 방법을 설명한다.
- **결과와 근거:** 결과의 범위, 조건, 출처를 함께 적는다.
- **남은 한계:** 아직 확인하지 못한 것과 일반화할 수 없는 범위를 구체적으로 적는다.

문제 해결 그림은 구조·흐름·시퀀스를 설명한다. 제품 화면은 서비스 섹션에 둔다. 그림과 화면에는 내용을 이해할 수 있는 대체 텍스트를 붙인다. 코드 캡처만으로 문제 해결을 대신하지 않는다.

## 수치와 출처

모든 수치는 해당 프로젝트의 `docs/facts/*.md`에 있는 기록과 맞춘다. 측정 조건과 출처 링크를 지표 가까이에 둔다. GitHub 파일 링크는 브랜치가 아니라 40자리 커밋 SHA로 고정한다.

지표의 종류를 구분한다. 같은 대상을 바꾸기 전후로 잰 값은 **전후 변화**, 같은 조건에서 여러 전략을 나란히 잰 값은 **대안 비교**, 한 번 확인한 수치는 **관찰값**이다. 대안 비교를 화살표로 적어 개선 전후처럼 보이게 하지 않는다. 예를 들어 낙관적 락 40%, 비관적 락 100%는 전략별 성공률이며 코드를 고쳐 40%에서 100%로 개선했다는 뜻이 아니다.

측정하지 않은 성능은 추정치로 채우지 않는다. 결과가 특정 부하, 합성 데이터, mock, 단일 실행에서 나왔다면 그 조건을 함께 밝힌다. `docs/facts/*.md`의 **싣지 않는 수치** 목록은 과거에 부인하거나 범위를 잘못 붙인 수치를 막는 기준이다. 숫자가 기록에 있다는 사실만으로 공개해도 되는 것은 아니다.

`npm run lint:writing`은 사례·프로젝트·대표 목록·이력서의 참조, 파일 경로, 수치 근거와 금지 수치를 검사한다. 화면에서 실제로 잘못 보이는 문장은 e2e에서도 확인한다. 검사 통과 후에도 새 주장과 원본 근거가 같은 의미인지 직접 읽는다.

## 표기

문체는 문장의 역할에 맞춘다. 서비스 설명은 자연스러운 서술형으로, 결과는 짧고 구체적으로 쓴다. 불릿 수와 제목 글자 수는 강제하지 않는다. 화살표 `→`는 전후 관계에만 쓰고 앞뒤를 띄운다. VU는 숫자와 띄어 쓴다. 네 자리 이상의 일반 숫자에는 쉼표를 사용한다. 조건이 많아지면 쉼표를 억지로 이어 쓰는 대신 문장을 나눈다.

## 화면 구성과 참고 (2026-10-03)

흰 바탕 #ffffff, 본문 #171a21, 보조 글 #555f70, 구분선 #dcdee8, 면 #f6f7fa, 강조 #0016ec를 사용합니다. Pretendard 하나로 제목·본문을 구분하며 본문 줄 길이와 행간을 우선합니다.

[Lee Robinson](https://leerob.com)의 짧은 소개와 바로 이어지는 글 목록, [Brittany Chiang](https://brittanychiang.com)의 프로젝트 맥락·실제 화면·개별 링크 배치를 직접 확인했습니다. 문구·경력·이미지를 가져오지 않았습니다. 과도한 번호·지표 카드 대신 서비스 화면 옆에서 목적·담당·판단·확인 결과를 읽습니다. 모바일에서는 설명과 사례 제목을 먼저 보여 주고 서비스 화면을 뒤에 배치합니다.

생각등대 가이드의 문제·해결·결과 흐름과 로컬 부하 실험을 사례 재료로 삼는 원칙을 적용합니다. 숫자를 먼저 정하거나 줄 수를 강제하지 않습니다. 가이드 전체와 강의 전체를 정독·시청했다고 주장하지 않습니다. README에는 서비스 소개, 기술 선택의 근거에는 이 사이트와 개발 문서를 사용합니다.

기존 사이트의 main·배포 주소는 보존하고 이 브랜치의 정적 산출물을 별도 Vercel Hobby 프로젝트에 배포합니다. 새 지출 한도는 0원입니다.
