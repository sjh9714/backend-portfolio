## 접근성 조회 병렬화 — measured (2026-08-08)

출처: `tech4good-2026/eta` `680a8d6` (브랜치 `perf/accessibility-fanout`) · `docs/PERF_RESULT.md`

### 무엇이 문제였나 (코드로 확인)

`backend/app/` 전체에 동시 실행 수단이 하나도 없었다.

```
asyncio.gather 0 · TaskGroup 0 · create_task 0 · asyncio.wait 0 · as_completed 0
```

`async def` 39개에 `httpx.AsyncClient`를 쓰면서 전부 순차로 기다렸다.
`providers/accessibility.py`의 `get_context`가 경로 후보마다, 그 안의 구간마다 `await`했고,
지하철 구간 **하나**가 서로 무관한 호출 5개를 또 차례로 기다렸다
(승·하차역 엘리베이터 2 + 승강기 목록 2 + 실시간 도착 1).

### 무엇을 했나

1. 구간별·구간 안의 독립 호출을 `asyncio.gather`로 묶음
2. 같은 역·정류장이 여러 경로 후보에 겹치면 한 번만 묻고 나눠 씀
3. provider마다 시간 한도(기본 3초)를 두고 넘기면 그 항목만 `UNKNOWN`으로 내림 —
   이 저장소가 원래 하던 "확인 못 한 것은 확인 안 됨"의 연장이다

### 어떻게 쟀나

같은 스크립트(`backend/tools/measure_accessibility.py`)를 before(`8102b7b`)와 after에서
각각 돌렸다. 외부 호출 1건당 **50ms 고정 지연을 주입**했고 케이스마다 5회 반복해 중앙값을 썼다.
Apple M4 · macOS 26.3.1 · Python 3.12.13.

| 지하철 구간 | 경로 후보 | 외부 호출 (전 → 후) | 대기 (전 → 후) |
| ---: | ---: | ---: | ---: |
| 1 | 1 | 5 → 5 | 258.0ms → **52.3ms** |
| 2 | 1 | 10 → 10 | 514.9ms → **52.5ms** |
| 4 | 1 | 20 → 20 | 1,031.2ms → **52.5ms** |
| 4 | 3 | 60 → **20** | 3,097.4ms → **51.9ms** |

**대기가 구간 수에 비례해 늘던 것이 구간 수와 무관해졌다.** 주입 지연이 50ms이므로
52ms는 "한 번 기다린 시간"이다. 후보 1개 기준 호출 수는 그대로다 —
줄인 것은 **기다리는 순서**이지 호출 자체가 아니다.

### 사이트에 쓸 때 반드시 함께 쓸 것

> ⚠️ **외부 응답 시간은 주입한 50ms 고정값이다. 실제 TMAP·서울 공공데이터의 응답 분포가
> 아니다.** 확인한 것은 호출 구조(기다림이 쌓이는가)이지 실제 응답 시간이 아니다.
> 처리량이나 동시 사용자 지표로 쓰지 않는다.
>
> `_get_elevator_rows`는 600초 캐시라 실제 운영에서는 엘리베이터 조회 상당수가 네트워크를
> 타지 않는다. 위 측정은 캐시가 없는 상태를 가정한 값이므로 실제 개선폭과 다를 수 있다.

## 확인된 설계 사실

### 개인별 이동속도 보정
- 이동 유형·보조기구·계단 회피·엘리베이터/저상버스 필수 조건을 프로필로 설정
- 평소 보행속도 + 안내 중 수집한 **유효 속도 표본**으로 도보 구간 ETA 보정
- 경사·보행환경 반영. **일반 ETA와 개인화 ETA를 함께 제공** (하나만 주는 게 아님)

### UNKNOWN을 일급 상태로 — ★ 서사의 핵심
원문 인용:
> "확인되지 않은 정보는 이용 가능으로 단정하지 않고 `UNKNOWN` 또는 주의 상태로 표시합니다."

→ 이것이 사이트 전체 주제 **"모르는 것을 모른다고 말한다"** 와 정확히 같은 사상이다.
billing-gateway의 "수치를 싣지 않은 이유", 포트폴리오의 claim boundary 원칙과 한 축으로 묶인다.

### 외부 API 통합
어댑터 계층으로 분리:
- TMAP — 대중교통·자동차·보행 경로
- 서울 버스 도착정보 · 저상버스 정보
- 서울 지하철 실시간 도착정보
- 서울 열린데이터광장·공공데이터포털 — 엘리베이터 및 교통약자 이용정보
- Kakao Local API — 장소 검색

### 재탐색
- 경로 이탈·대중교통 놓침 감지 → 재탐색 제안
- 현재 위치를 새 출발점으로 경로·ETA 갱신
- **원본 위치 좌표는 안내 중 계산에만 사용하고 영구 저장하지 않음** (프라이버시 설계)

### 교통수단 최적화
- 대중교통·도보·택시를 시간·비용·접근성 관점에서 비교
- 이용 가능한 대중교통 경로가 없으면 택시 또는 **장애인 콜택시** 대안 제시

   실제 TMAP·Kakao·서울시 운행정보가 아니며 **화면이나 발표에서 실제 정보처럼 표시하면 안 됩니다**."

### 카카오 키가 필요한 이유 — 목 fixture로는 못 채운다

`services/kakaoPlaces.ts`가 브라우저에서 **카카오 SDK를 직접 부른다**
(`window.kakao.maps.services.Places`). 백엔드 라우트는 9개인데 장소 검색이 아예 없다 —
프로필·경로·안내뿐이다. 그래서 `mocks/places/search.success.json` fixture가 있어도
프론트가 그 경로로 가지 않는다. 키 없이는 검색에서 막혀 경로 화면에 도달할 수 없다.

설정: 카카오 개발자 콘솔 앱 `Songsim Campus MCP`(ID 1404349)의 JavaScript 키에
`http://localhost:5180`·`http://localhost:5173`을 JS SDK 도메인으로 등록했다.
카카오맵 무료 쿼터는 **계정당 앱 하나**에만 주어지고 이 앱이 이미 갖고 있다.
새 앱(`My ETA`, ID 1536297)을 만들어 봤지만 무료 쿼터를 받을 수 없고 월렛 연결(과금)을
요구해 쓰지 않았다. 그 앱은 비어 있는 채로 남아 있다.

**키는 `frontend/.env`에만 둔다.** `frontend/.gitignore:7`이 `.env*`를 무시한다.

## 프론트를 다시 짓지 않기로 한 이유 (2026-08-07)

concert·chat·eta 셋을 제품으로 다시 짓기로 했고, concert와 chat은 했다.
**eta는 하지 않았다.** 판단 근거를 적어 둔다.

### 1. eta에는 그 문제가 없었다

'실제 서비스가 아니라 기능 테스트 같다'는 지적은 데이터가 얇아서 생긴 것이었다.

| | 문제 | 조치 |
|---|---|---|
| concert | 회차당 **50석**, 공연 2개 | 436석·공연 6개로, 매진 자리 섞음 |
| chat | 대화 **1개**, 메시지 3개 | 대화 5개·메시지 22건·닷새치 |
| **eta** | — | 실제 카카오 지도·장소 검색, 세 모드 각각 다른 접근성 판단 |

eta는 세 탭이 모두 다른 이야기를 한다.

- 대중교통 — 일반 11분 vs 개인화 18분, 경사·노면·턱낮춤 근거
- 택시 연계 — "이동 보조기구 탑승 가능 차량을 보장하지 않습니다"
- 안전도보 — 일반 2분 vs 개인화 6분, 계단을 피하는 경로

### 2. 손대 봤고, 되돌렸다

경로 옵션이 모드당 하나뿐이라 정렬 규칙이 화면에서 보이지 않는 게 아쉬웠다.
그래서 목 프로바이더에 버스 대안 경로를 넣어 봤다.

결과: 개인화 소요가 **1,981,844초(약 23일)** 로 나왔고, 팀원이 만든
하이브리드 택시 추천까지 끌어들여 TRANSIT 응답에 택시가 섞여 나왔다.
개인화 엔진은 `personalization.py` 525줄 중 126줄이 팀원 것이고,
`_hybrid_taxi_route`는 100% 팀원 것이다 (「저작자 경계」 참조).

**남의 코드 안쪽을 더듬어 가짜 경로를 만들어 넣지 않는다.** 되돌렸다.

### 3. 해커톤 결과물이다

24시간 안에 만든 것이다. 지금 다시 지으면 저장소가 더 이상 그때 만든 것을 보여주지 않는다.
concert·chat은 개인 저장소라 계속 고쳐 나가는 게 자연스럽지만, eta는 그 시점의 기록이기도 하다.

### 다시 짓는다면

모드당 경로를 여럿 주려면 개인화 엔진이 버스 구간을 어떻게 다루는지부터 읽어야 한다.
그건 팀원 영역이라 먼저 물어보고 시작할 일이다.
