## 백엔드 현황 — 왜 다시 만드는가

`finmate-api`는 Java 21 · Spring Boot, 165파일에 통합 테스트도 있다. 그런데:

```
finmate-api 도메인   quests · records · goals · rewards · mate · auth · data · documentation
finmate-app 기능     diary · feed · insights · mate · missions · my · onboarding
```

**IA가 다르다.** `finmate-api`는 "vNext"라는 별도 제품 정의로 설계됐고,
`finmate-app`은 백엔드 없이 목으로 돌아갔다. **둘은 한 번도 연결된 적이 없었다.**
(2026-08-07에 처음 붙여 봤다 — 아래 「실제로 붙여 본 결과」)

커밋도 3일(07-13~07-15) 만에 `codex/` 브랜치로 쌓였다 —
`68a2f0e feat: integrate locked synthetic data release` 한 커밋이 **87파일 5,624줄**이다.

그래서 재구현의 정의: **`finmate-app/src/data/`를 계약으로 삼아 프론트가 실제로 붙는 백엔드를 만든다.**

### 성능 — 예상이 틀렸다

발표자료 13쪽의 "매 렌더 원장 재계산"을 첫 성능 지점으로 잡았는데 **아니었다.**

| | p50 | p95 |
|---|---|---|
| 마이 탭 (개인) | 0.66~0.71ms | **0.96ms** |

한 사람의 한 달은 32행이라 `(persona_id, occurred_on)` 인덱스가 buffer 4개만 읽는다.
**여기는 고치지 않았다.**

비싼 곳은 또래 비교였다. 싼 것부터 순서대로 쟀다.

| 방법 | p50 | 추가 저장 | 판단 |
|---|---|---|---|
| 원장 직접 집계 | 32.5ms | — | 기준 |
| 쿼리 수정 (`count DISTINCT` 제거) | 28.0ms | 0 | 디스크 정렬 2,496kB → 메모리 142kB |
| + 커버링 인덱스 | 24.0ms | 50MB | **미채택** |
| **사람×월 사전 집계** | **0.72ms** | **1.9MB** | **채택** |

읽는 버퍼 23,326 → 206. 두 방식의 결과가 소득대 6개 그룹 전부 일치.

### AI 그림일기

`PENDING → SUBMITTED → READY / FAILED` 상태 기계. fal.ai 큐(`fal-ai/flux/dev`).
실제 생성 확인: **4.5초**.

- 멱등성 — `(persona, date)` 유니크. 동시 8회 요청에도 한 장
- 재시도 — 3회, 넘으면 이유를 남기고 FAILED
- 회수 — 5분 넘게 SUBMITTED면 되돌림
- 그림체는 날짜에서 결정적으로 고른다

**그림체는 7종에서 6종으로 줄였다.** 로우폴리 3D가 `flux/dev`로 나오지 않는다
(재질 앞세우기 · 매끄러움 배제 · 사물 장면 세 번 다 실패). 안 되는 그림체를 두면
그날마다 조용히 다른 그림이 나가므로 뺐다.

프롬프트에서 배운 것: **재질을 먼저 말해야 한다.** "hand embroidery on linen" 같은
형용사 나열은 그냥 깔끔한 디지털 일러스트를 낳는다. "이 이미지가 무엇으로 만들어졌는가"를
앞세우니 실이 도드라졌다.

## 또래 비교 사전 집계 — measured (§3 · 2026-08-08 옮겨 적음)

출처: `gaga-studio/finmate-api` `169c037` · `docs/PERF_RESULT.md` §3

### 왜 비쌌나

조건이 `occurred_on BETWEEN`뿐인데 인덱스는 `(persona_id, occurred_on)`이라 선행 컬럼이 없어
못 탄다. 원장 전체를 훑고 디스크에서 10,991 버퍼를 읽었다. 여기에 `count(DISTINCT p.id)`가
`(income_band, id)` 정렬을 강요해 `work_mem`을 넘겨 **디스크 정렬 2,496kB**가 났다.

### 싼 것부터 차례로 재봤다 (원문 §3-2 표)

| 방법 | p50 | 추가 저장 | 판단 |
|---|---:|---:|---|
| 원장 직접 집계 | 32.5ms | — | 기준 |
| ① 쿼리 수정 — persona 선집계로 `count(DISTINCT)` 제거 | 28.0ms | 0 | 디스크 정렬은 없앴지만(2,496kB → 메모리 142kB) Seq Scan이 남음 |
| ② + 커버링 인덱스 `(flow, occurred_on) INCLUDE (persona_id, amount)` | 24.0ms | **50MB** | Bitmap Index Scan을 타지만 여전히 10만 행을 집계 |
| ③ **사람×월 사전 집계 테이블** | **0.72ms** | **1.9MB** | **채택** |

> 원문: *"②는 채택하지 않았다. 50MB를 쓰고 8.5ms를 벌었는데, ③은 1.9MB로 31.8ms를 번다."*

### 채택안 (`persona_month`, §3-3)

| 항목 | 값 |
|---|---|
| p50 / p95 | **0.72ms** / 0.95ms — 기준 대비 **45배** |
| 행 수 | **14,000** (2,000명 × 7개월) |
| 크기 | 1,992 kB (원장 **179MB**의 **1.1%**) |
| 전체 재생성 | 401ms |
| 읽는 버퍼 | 23,326 → **206** |

> 원문: *"한 달치 **105,484행**이 접히고 나면 2,000행이다."*

§3-4에서 두 방식의 결과가 **소득대 6개 그룹 전부 일치**하는 것을 대조했다
(평균은 반올림 차이만). `PeerCompareIntegrationTest`가 매번 원장을 직접 세어 집계와 대조한다.

**개인 화면은 고치지 않았다.** `(persona_id, occurred_on)` 인덱스가 그 접근 패턴을 정확히
덮어 버퍼 4개만 읽는다(p95 0.96ms). 원문이 *"측정을 먼저 한 이유가 이것이다"*라고 적고 있다.

| 피드 (그룹·메이트) | 9.92ms | 27.89ms |
| 미션 | 8.53ms | 25.77ms |
| 인사이트 투영 | 5.34ms | 19.52ms |

> 원문: *"§3에서 잰 0.72ms가 50 VU에서 p95 25.39ms가 됐다.
> 순차 호출과 동시 호출은 다른 숫자다."*

VU마다 다른 계정으로 가입해 서로 다른 원장을 본다 — 같은 계정을 나눠 쓰면 캐시가 없는데도
있는 것처럼 빨라 보인다는 이유가 원문에 적혀 있다.

**사이트에 쓸 때는 §3(0.72ms)과 §4(25.39ms)를 반드시 함께 쓴다.** 0.72ms만 쓰면
동시 사용자 환경의 수치처럼 읽힌다.

### 붙지 않는다 ⚠️ — 여기가 사실이다

`src/data/source.tsx`(106줄)가 서버로 넘기는 것은 **세 가지뿐**이다.

| 항목 | 상태 |
|---|---|
| `today` (기준일) | 서버 |
| `budget(period)` | 서버 |
| `topPurchases(period, n)` | 서버 |
| 그 외 전부 | **목** |

이 소스를 쓰는 화면도 `MyPage` · `MetricCards` · `LinkedListPanel` 셋뿐이다.

브라우저로 다섯 탭을 모두 눌러 확인했다. **최초 `overview` 한 번 말고는 API 호출이 없다.**

| 탭 | 새 API 호출 | 화면 값 |
|---|---|---|
| 마이 | (최초 overview) | 일부 서버 |
| 피드 | 없음 | 목 |
| 분석 | 없음 | 목 — "지출 13,900원 · 예산 31%"는 목 값이다 |
| 미션 | 없음 | 목 — 같은 13,900원 |
| 기록 | 없음 | 목 — 7월 23일 기준 |

즉 **또래 비교·피드·미션·인사이트·다이어리 API는 만들어 두었지만 앱이 부르지 않는다.**
백엔드에 있는 것과 화면에 뜨는 것이 다르다.
